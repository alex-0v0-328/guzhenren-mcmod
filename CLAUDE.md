## Checks and shipping

Two one-command tools replace hand-run Gradle chains and the manual commit ritual (Alex, 2026-09-26). They run on Windows Python, which both runtimes call directly, and each writes one log, `C:\workspace\Dev\Projects\_Temp\<project>\logs\check.log` or `ship.log`, which its next run overwrites. Read the log, report from it, then delete it. While one tool drives Gradle, the other refuses to start (`gradle.lock`), so parallel sessions never collide.

`python tools/check.py` runs every stage in this order. Naming stages runs only those, `--headless` skips the client, and `--list` describes each stage. Times are warm-cache; a cold build adds 2–3 minutes.

| Stage      | What a pass proves                                                                                                                                                              | Warm time |
|------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------|
| `build`    | Compile and jar pass, plus L1 `pureTest` and L2 `test` JUnit; the wiki gate `-PwikiDir` is on whenever the wiki exists                                                          | 0–2 min   |
| `gametest` | Every L3 `@GameTest` passes on the dedicated GameTestServer                                                                                                                     | ≈0.5 min  |
| `data`     | `runData` reproduces `src/generated` byte for byte (the CI drift check); a rewrite fails and lists the files to review                                                          | ≈0.3 min  |
| `server`   | `runServer` in a throwaway Temp world without the pack mirror: boot, summon every mod entity, place every mod feature, load every Gu World dimension, tick 20 s, stop over RCON | ≈0.7 min  |
| `client`   | `runClient` with the `run/` pack reaches the title screen and stays alive 20 s, then closes; opens a window, and skips while a game from this checkout runs                     | ≈0.8 min  |

- During iteration, run the stages the change touches; the `commit-push` skill runs the full check before shipping. Visual and feel acceptance in `runClient` stays Alex's.
- The game stages (`gametest`, `server`, `client`) first run `clean build` in `../guworld` and load its jar; without that project they fail.
- `python tools/ship.py` is the commit tool behind the `commit-push` skill, which owns the flow and describes every stage.
- Both tools also drive the sibling repositories (registry `gzr_env.PROJECTS`): Gu World with `--project guworld` (check `build` and `data`; its ship mirror runs `build` as its CI does plus the local `data` drift check) and Camera Shift with `--project camerashift` (check `build` with its local JUnit; its ship mirror runs `build` as its CI does, then again with `src/test` copied in). A repository or remote with no commit yet ships too.
- This IDEA window links Gu World and Camera Shift as Gradle projects (Alex, 2026-10-01). Their run configurations carry a prefix and a folder (`Gu World Client`, `Camera Shift Client`, via `ideName` / `ideFolderName`), so GZR's plain `Client`, `Data`, `Server` and `GameTestServer` stay its own; a new linked project needs the same.
- The test suites are local-only (Alex, 2026-09-27; the siblings too from 2026-10-01): `src/test/` is gitignored, GitHub Actions only compiles, packages and checks datagen drift, and the ship mirror is where tests guard a push. They have no remote copy and no version history from that date on.
- The siblings follow this repository wherever GitHub sees them (Alex, 2026-10-01): the same `.gitignore` sections, `.gitattributes`, `.editorconfig`, `LICENSE.txt`, the README set (`README.md` in Simplified Chinese, Alex's source, with `README.zh-TW.md` and `README.en.md` translated from it; 2026-10-02), a tracked `CLAUDE.md` and the `.claude/` cloud files, and the code conventions of Language and style, which each sibling's `CLAUDE.md` condenses for cloud sessions.

## Language and style

- Chat in Chinese (zh-CN); think in English, the model's strongest language — only the reply is Chinese (Alex, 2026-09-25). Code, comments and commit messages in American English. `CLAUDE.md`, `rules/` and `.claude/skills/` are written in English, `reference/` in Chinese.
- Terms come from the language provider, `en_us.json` and the wiki《原著词汇 与命名》 — never invent bilingual pairs (known trap pairs in reference《写作与命名》).
- New code matches its neighbors' comment density, naming and idiom; formatting follows `.editorconfig`; comments explain non-obvious reasons only. No bulk reformat, no project-wide IDEA "cleanup code". Substantive conventions (`@NotNull`/`@Nullable`, import ordering, Javadoc FQN rules) live in reference《写作与命名》.
- Cross-references name the heading — `CLAUDE › Boundaries`, reference《心跳顺序》, `[[待定设计#…]]` in the wiki — never a section sign or a section number, and headings carry no number prefixes (Alex, 2026-09-24).
- Markdown tables stay aligned (Alex, 2026-10-01): a padded table pads every column to its widest cell in display width (CJK counts 2) and its separator to that width plus two dashes, tight `|---|` in rules files and READMEs, spaced `| --- |` in the wiki; compact `|---|` tables stay compact. Any added or edited row re-pads the whole table: after touching a table, `python tools/md_tables.py <file>` must report nothing (`--fix` re-pads).
